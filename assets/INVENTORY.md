## The finding that shaped this pass

**Most photography on this reference is not an `<img>`.** GoDaddy paints photos as
`div[role="img"]` carrying a CSS `background-image`. Keying an inventory on `document.images`
alone would report the home page as having exactly two pictures — and both of them are the
same wordmark, rendered once for the desktop bar and once for the nav drawer. The probe
enumerates `<img>` + `srcset` + `<source>` **and** `url()` on `backgroundImage`, `maskImage`,
`borderImageSource` and `listStyleImage` across every element. Nine of the sixteen REPLACE
slots on this site are CSS backgrounds; the hero, the `/about` statement band and the
`/services` CTA banner are all background-image bands with no `<img>` in them at all.

Two instrument defects were fixed in the shared harness to make this measurable, and both
are general rather than site-specific:

1. **Transform-chain URLs.** GoDaddy isteam URLs end in a resize token, not a filename —
   `.../Blog%20Banner.png/:/rs=w:200`. Taking the last path segment collapsed the six
   distinct `/services` card photos into one slot called `rs=w:388,h:194,cg:true`.
2. **The CDN host looked like a filename.** `img1.wsimg.com` ends in `.com`, so the
   extension test matched the *host* and every extensionless asset on the CDN
   (`/isteam/getty/2157587620`, `/isteam/stock/ArQdAzZ`) merged into one row.

A third change was needed for correctness rather than parsing: slot rules can now be
**route-scoped**. Three reference files appear in two bands with different fates — the
`/about` hero photo is reused inside `/contact`'s deleted Locations grid, and all three home
blog thumbnails reappear in `/about`'s deleted blog feed. Un-scoped, each pair merged into a
single slot and the merge (which keeps the widest geometry per breakpoint) handed the
**retained** slot the **deleted** band's dimensions.

## Near-white repaint

**None fired on this site.** The reference is a dark theme — band backgrounds are
`rgb(22,22,22)` / `rgb(0,0,0)` / `rgb(17,17,17)` — so every sampled dominant colour sits well
below the `placeholderMaxLum` of 0.62. The lightest sample in the set is `#bcc4cd`
(relative luminance ≈ 0.55, the three `/about` photos against that route's one white band),
which is a mountable mid-light neutral and needs no repaint. The mechanism is configured and
live (`placeholderMaxLum` / `placeholderTargetLum` in `harness.config.mjs`); it simply had
nothing to correct. **Zero slots were left deliberately unapplied.**

## What is NOT in this file

Placeholder SVGs are flat fills with the slot ID and pixel dimensions as text, generated
locally into `public/placeholders/`. **No external placeholder service is contacted**, at
build time or at runtime — there is no `placehold.co`, no `picsum`, no image CDN. The
generator is `placeholderSVG()` in the shared harness and it writes a `<rect>` and two
`<text>` nodes, nothing else.
